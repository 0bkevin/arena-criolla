Preparación y límites reales

- La numeración representa un orden propuesto de integración, no un historial de commits que ya exista.
- Registrar cambios verificables; no inventar fechas, hashes ni snapshots perdidos.
- No usar git add . para ejecutar esta lista. Muchos commits comparten App.tsx, engine.ts y los catálogos JSON.
- Para archivos nuevos sin seguimiento, git add -p no divide su contenido hasta usar git add -N ruta. Después seleccionar hunks reales; las filas JSON y los casos de funciones requieren atención a la sintaxis.
- Cuando un archivo entero pertenece a varias unidades, preparar versiones incrementales completas y revisarlas en un checkout temporal. git add -p por sí solo no reconstruye versiones antiguas ni resuelve dependencias de imports.
- Introducir contratos, tipos y referencias antes de los usuarios de cada función. Revisar el árbol que quedará en cada commit, no solo el working tree final.
- Ejecutar comprobaciones del bloque al completarlo; un test global del elenco de 41 falla legítimamente antes de que entren todos sus personajes.
- Añadir las pruebas junto con la función cuando sea posible. Los commits de test finales cubren aserciones globales y cruces restantes; fusionar cualquier unidad que no deje un diff real.
- Las revisiones Capriles v3/v21/v22 y Óscar v24/v25 conservan assets. Reconstruir sus pequeñas referencias de catálogo/manifiesto si se desean commits separados; si se registra solo el final, agrupar esas revisiones.
- Las UI descartadas sin fuente completa se documentan como estudios. El snapshot v26 sí está archivado, pero la rama actual conserva el rollback aprobado; no reactivar el experimento para fabricar historia.
- No incluir node_modules, dist ni secretos; los archivos de investigación, fuentes originales y grabaciones son material de soporte, no todo forma parte del runtime.
- Antes de crear cada commit: revisar git diff --cached, usar su mensaje completo y comprobar el árbol staged. Los mensajes están disponibles en commits[].message.
- El primer hito jugable depende de cimientos, contenido mínimo, assets e integración de UI. Ajustar o agrupar los primeros commits para que no se introduzcan imports a archivos que todavía no existen.
- No se hizo staging ni se crearon commits. Esta tarea solo genera la propuesta y sus mensajes.
