# Arena Criolla creator-pipeline adversarial review

Reviewed 2026-10-17. The feature described as a “RAG pipeline” is a LangGraph character-generation flow: reference-photo normalization, a structured design response, an image-edit request, sprite validation/packing, and a gameplay check. I found no retriever, vector store, or retrieval-augmented context path.

Testing used temporary SQLite/data directories, ephemeral localhost ports, and deterministic fake providers. No live AI requests or billing were used. Severity describes the operational impact; confidence describes the evidence. For fixed findings, severity is the baseline impact before the fix.

## Open findings

### P2 — High confidence: Retired published art remains publicly retrievable and cannot be purged

Deleting a published character marks it archived and intentionally retains its generated directory (`server/creator/router.ts:591-607`). The owner helper then hides archived rows as 404 (`server/creator/router.ts:137-145`), so the owner cannot issue another delete to permanently remove the directory. The public asset route accepts archived rows and returns them with public caching (`server/creator/router.ts:638-655`). Archived rows are also excluded from the per-owner active-character count (`server/creator/database.ts:129-135`), so that limit does not cap lifetime archive growth.

Reproduction: I created and published a character, then deleted it. Create returned 202, publish 200, retire 200, later owner detail 404, and an anonymous GET of `/api/community/assets/<id>/sprite.webp` returned 200 with `Cache-Control: public, max-age=86400`; the row remained archived. The uploaded photos were removed while generated art remained served. Repeated create/publish/retire grows archived rows and image files without a lifetime quota or cleanup path. The README says art is retained for ongoing matches, but there is no match-reference tracking or expiry cleanup. Establish a retention policy and purge assets once references expire, or add a deliberate owner-controlled purge path.

### P3 — High confidence: A persistence error permanently stops generation until process restart

If the worker cannot persist a failed job, it stops admission to prevent more paid work (`server/creator/worker.ts:127-146`). Capabilities then report generation unavailable (`server/creator/router.ts:342-347`), and create/retry return 503. There is no in-process restart/recovery path, so even a transient SQLite write error disables generation until restart. The only signal is the log at `server/creator/worker.ts:142-146`; `/api/health` is intentionally arena liveness and stays healthy.

Reproduction: in a child process, a SQLite trigger rejected the compensating update to mark a job failed. The process survived, a subsequent create returned 503, and the worker stayed stopped. This is fail-closed but requires an operator to notice the log and restart the process.

### P3 — High confidence for the code assumption; impact applies only to unsupported multi-process deployments

The worker queue, active-job map, concurrency, and upload reservations are in process memory (`server/creator/worker.ts:82-115`; `server/creator/router.ts:181-201`). The README explicitly limits this release to one process and says not to add replicas (`README.md:51-55`). If deployed with multiple workers/replicas anyway, each process has its own capacity limit and queue, so aggregate concurrency/capacity multiply and jobs are not coordinated. On process restart, pending work is marked failed and waits for its owner to continue (`server/creator/router.ts:266-272`). Keep deployment to one process unless queue/admission ownership moves to shared coordination.

### P2 — Medium confidence: An interrupted upstream request can still have ambiguous billing

The provider sends abort signals and disables automatic SDK retries (`server/creator/provider.ts:38-39`, `server/creator/provider.ts:99-100`). The worker enforces a total deadline and returns failure when it expires (`server/creator/worker.ts:117-140`; `server/creator/router.ts:164-166`). A fake provider that ignored abort returned late and did not advance or overwrite the failed job, but the application cannot establish whether an upstream service completed or billed a request before observing cancellation. A user who deliberately retries after a timeout may make another paid call. The UI warns about possible interrupted image-request cost; this is a limit of the observed client-side cancellation semantics, not a claim that a particular request was billed.

Reproduction: block a provider call beyond the job deadline, then resolve it late. The test verifies failed status, no `source_path`, and no automatic second draw. No live service was used, so billing behavior itself remains unverified.

## Findings fixed during this review

- **P1 baseline, fixed — High confidence: Unbounded paid-work queue.** Before the changes, 30 simultaneous valid submissions all returned 202 while one fake design call was blocked; one job was active and 29 waited in memory. Each could later start paid design/image requests. The current worker limits concurrency and queue execution (`server/creator/worker.ts:82-115`), while admission checks capacity (`server/creator/router.ts:181-195`) and rolling attempt quotas (`server/creator/database.ts:91-123`). The same 30-submission probe now accepts 12 and returns 503 for 18 while the two fake active workers are blocked. The limit is per process, as noted above.
- **P1 baseline, fixed — High confidence: Failure persistence could crash Node.** A child-process trigger rejecting the failed-status update reproduced the former unhandled worker exception. The current worker catches that error and stops admission (`server/creator/worker.ts:127-146`); the same child process stays alive and new jobs receive 503. This replaces a process crash with the manual recovery limitation above.
- **P2 baseline, fixed — High confidence: Retry could make a second paid image request after a DB pointer write failed.** Reproduction: let a valid image response write to disk, reject the following `source_path` database update, then retry. Before the fix, the retry drew again. The current draw node uses a unique temporary file plus atomic rename and reuses an existing completed image (`server/creator/pipeline.ts:217-248`). The regression test verifies ready status and one draw call after retry.
- **P2 baseline, fixed — High confidence: Invalid cached image bytes could poison every retry.** Reproduction: return malformed image bytes, let packing fail, then explicitly retry with a valid atlas. Packing errors are normalized to `SpriteValidationError` (`server/creator/sprites.ts:18-45`); the graph removes invalid cached input (`server/creator/pipeline.ts:250-269`). The test verifies the bad file is removed and the second valid fake atlas completes.
- **P2 baseline, fixed — High confidence: A failed character-row insert could consume quota without accepting a job.** A trigger rejecting `INSERT INTO characters` previously produced a 500, consumed the one-attempt daily quota, and made the next valid request return 429. Reservation and the synchronous row-creation callback now share one SQLite transaction (`server/creator/database.ts:91-122`; `server/creator/router.ts:492-505`). The regression test verifies rollback leaves zero attempts and the subsequent accepted row reserves one.
- **P2 baseline, fixed — High confidence: A worker stop during multipart upload could still return 202 for a job that would never run.** Reproduction: admit a held multipart body, stop the worker by rejecting a compensating DB write for a separate job, then finish the upload. Before the fix, the second request returned 202, left a queued row, and made no provider call. The post-parse check now returns 503 and removes the uploaded files if the worker stopped (`server/creator/router.ts:481-489`). The permanent regression test asserts 503, no second row, and zero second provider calls.
- **P3 baseline, fixed — High confidence: Queue wait was excluded from the advertised 300-second job deadline.** Before the fix, each timer began only after dequeue; with capacity 12 and concurrency 2, a final-wave job could wait up to 25 minutes and then run for another 5 minutes before timing out (`server/creator/worker.ts:25-34`). The worker now stores a monotonic deadline at enqueue and starts execution with only the remaining budget (`server/creator/worker.ts:98-108`, `:126-137`); if it has expired, `abortable` prevents the provider callback from starting. Regression: with one worker slot occupied and a second job queued, I simulated a 120 ms event-loop stall against an 80 ms deadline; the queued job failed with `TimeoutError` and the fake provider was called only for the first job (`tests/adversarial-creator-v31.test.ts`, “queued creator work expires before provider start after an event-loop stall”).
- **P3 hardening, fixed — High confidence: First design output needed a graph-boundary schema check.** A malformed initial design from a provider could otherwise progress past provider-specific validation. The graph now parses both first and resumed designs before saving (`server/creator/pipeline.ts:195-205`). A fake design with an overlong title fails before any draw request; the test observes zero draw calls.

## Input, auth, and provider-contract observations

Uploads are limited to three files of 8 MiB each, two concurrent uploads, a body deadline, and pixel limits; decoded formats are checked instead of trusting MIME labels (`server/creator/router.ts:403-479`). The adversarial suite rejects malformed/oversized photos before provider work. Markup and prompt-injection text stay bounded character data; no `dangerouslySetInnerHTML` or `innerHTML` sink was found in the client paths checked. Ownership checks protect detail and private reference-photo routes (`server/creator/router.ts:137-145`, `:616-626`).

The installed OpenAI SDK contract tests use an ephemeral local HTTP server and a fixture key. They verify Responses schema/image payload shape, image-edit parameters, abort release, and that a 503 is not retried into another request (`tests/provider-contract.test.ts:72`, `tests/provider-contract.test.ts:137`, `tests/provider-contract.test.ts:160`). These tests cover the SDK wire path without live credentials; they do not establish real model output, upstream availability, billing outcomes, or likeness quality.

## Workload and verification

The latest adversarial admission run measured **n=12 accepted submissions, p50 6.1 ms and p95 45.8 ms**. Workload: 30 sequential local HTTP multipart submissions with a small JPEG, isolated SQLite and Sharp processing, two fake design calls blocked, ten jobs queued, and no real provider call. This is local admission/response latency only, not upstream generation latency. A prior combined creator-suite run measured p50 8.7 ms/p95 56.5 ms under additional scheduler/test load. These synthetic figures do not predict OpenAI response time.

The adversarial suite passed **12/12** after the enqueue-deadline change and test formatting. An earlier `npm run test:creator` passed 31/31 before the latest race and provider-contract additions. The root agent reports 6/6 resilience tests and 3/3 provider-contract tests passing; the final combined run is owned by the root. `npx tsc --noEmit` passed before the final formatting-only changes.

**CI does not validate live OpenAI responses, actual upstream billing/cancellation outcomes, or generated-image likeness and art quality.** This is a P3 validation gap with high confidence: the workflow runs `npm test`, asset checks, build, and Docker smoke routes (`.github/workflows/ci.yml:15-31`), and the provider tests use only a local mock server. The workflow was not run during this review. I did not run a separate Docker build with 248 MiB free; the root agent attempted it and reports an `ENOSPC` failure, so container-build validation remains incomplete in this checkout.

RISKIEST LINE: server/creator/router.ts:641 — archived creations are explicitly allowed through the anonymous asset check, while owners have no route to revoke or purge the retained generated art.
