# Arena Criolla game and network review (v31)

Reviewed the shipped Node/Express/WebSocket server, shared deterministic combat engine, and React mobile controls. The pasted payment/cloud incidents were treated as review prompts only. The README explicitly describes local wins as unverified and says there is no ranking, so client-supplied wins are not reported as a ranked-integrity defect.

## Findings fixed in this review

- **Medium severity, high confidence — invite codes were guessable.** The prior six-hex-character room code had 24 bits of entropy. One client could submit at most 180 messages per second under the old message cap, so 8.39 million distinct guesses would take about 13 hours at that rate if fully serviced; this is arithmetic, not a measured attack rate. Multiplying by the 300-connection ceiling is only a theoretical upper bound, not a throughput result. Codes now use 16 cryptographically random bytes (32 hex characters) in [server/index.ts:331](/home/ubuntu/.t3/projects/vepol/server/index.ts:331), with shared validation and normalization in [shared/room-code.ts:1](/home/ubuntu/.t3/projects/vepol/shared/room-code.ts:1) and a 32-character UI contract in [src/App.tsx:861](/home/ubuntu/.t3/projects/vepol/src/App.tsx:861). The isolated test confirms a six-character prefix cannot join, while the full code can.

- **Medium severity, high confidence — a `list` flood amplified into a broadcast storm.** Before the fix, each accepted `list` request serialized and broadcast the room catalog to every connected socket. In an isolated fixture with 64 peers and 32 rooms, 180 requests caused 11,520 recipient-send attempts and took 687.1 ms to receive the requester’s replies. The server now rate-limits `list` to five replies per second and replies only to the requester; meaningful room changes are coalesced for 100 ms and share one serialized snapshot ([server/index.ts:126](/home/ubuntu/.t3/projects/vepol/server/index.ts:126), [server/index.ts:142](/home/ubuntu/.t3/projects/vepol/server/index.ts:142), [server/index.ts:309](/home/ubuntu/.t3/projects/vepol/server/index.ts:309)). Repeating the same safe fixture accepted five replies, sent zero room-list messages to the other 63 peers, emitted 44,730 reply bytes, and took 11.4 ms for those replies. Community snapshots are also serialized once per catalog mutation rather than once per socket ([server/index.ts:105](/home/ubuntu/.t3/projects/vepol/server/index.ts:105)).

- **Medium severity, high confidence — unknown HTTP upgrade paths kept untracked sockets open.** A raw WebSocket upgrade to `/unexpected` previously received no response and was not entered in the WebSocket client cap. The isolated probe observed no response after 500 ms. Unknown paths now receive a 404 and the server destroys the socket after writing; the 300-client rejection follows the same bounded-close path ([server/index.ts:221](/home/ubuntu/.t3/projects/vepol/server/index.ts:221)). The regression test leaves a raw TCP peer half-open and verifies the HTTP server’s connection count returns to zero. The dev-only Vite HMR root protocols remain allowed.

- **Low severity, high confidence — the authoritative loop did not enforce its declared 60 Hz units.** The old code stepped once per `setInterval(1000 / 60)` callback; with a 16 ms callback cadence, that is 62.5 steps per second and would advance a 5,400-tick timer in 86.4 seconds. This is the timer’s theoretical rate at that cadence, not a production-host measurement. The loop now uses monotonic elapsed time and a fixed 1/60-second accumulator, with at most five catch-up steps before dropping excess backlog ([server/ticker.ts:16](/home/ubuntu/.t3/projects/vepol/server/ticker.ts:16), [server/index.ts:464](/home/ubuntu/.t3/projects/vepol/server/index.ts:464)). Deterministic tests produce exactly 3,600 ticks over 60,000 ms for callback cadences of 8, 10, 16, 17, and 33 ms, and cap a 10-second stall to five steps ([tests/scheduler.test.ts:5](/home/ubuntu/.t3/projects/vepol/tests/scheduler.test.ts:5)).

- **Medium severity, high confidence — backpressure could silently lose reliable state transitions.** When a socket crossed the 256 KB send-buffer threshold, the prior helper dropped every message type. If `start` or the corresponding room update were dropped, the client remained in its stale lobby: later `state` messages only update `state.current` and do not create the mounted match. The server now drops only replaceable simulation-state frames and terminates a slow peer when it cannot send a reliable room/control message or community snapshot ([server/index.ts:83](/home/ubuntu/.t3/projects/vepol/server/index.ts:83), [server/index.ts:93](/home/ubuntu/.t3/projects/vepol/server/index.ts:93)). An isolated client-path test injects the threshold, confirms the slow host reconnect path closes, and verifies the other player receives `opponent-left` ([tests/adversarial-game-v31.test.ts:162](/home/ubuntu/.t3/projects/vepol/tests/adversarial-game-v31.test.ts:162)). The threshold test is deterministic; it does not model a real mobile radio or constrained WAN.

## Other adversarial checks

- A 5,000-byte WebSocket frame was closed with code 1009 against the server’s 4,096-byte `maxPayload` limit ([server/index.ts:79](/home/ubuntu/.t3/projects/vepol/server/index.ts:79)). Malformed JSON produced an error without mutating the match; a structurally invalid input was inert. A valid right-move input changed only its owning room in a 24-room fixture.
- Under that isolated fixture, 48 connected game peers in 24 simultaneously playing rooms advanced 60 ticks over 1,000.6 ms (60.0 Hz after normalizing by measured elapsed time); room tick counts differed by at most one. `/api/health` took 13.8 ms on loopback. These numbers describe one local process and this fixture, not a production capacity claim.
- The React touch component uses independent pointer IDs, pointer capture, and releases on pointer-up, pointer-cancel, lost capture, reset, disabled-state change, and unmount ([src/components/TouchControls.tsx:38](/home/ubuntu/.t3/projects/vepol/src/components/TouchControls.tsx:38)). Game lifecycle code releases inputs on pause, orientation change, blur, pagehide, hidden documents, and unmount ([src/components/Game.tsx:115](/home/ubuntu/.t3/projects/vepol/src/components/Game.tsx:115), [src/components/Game.tsx:223](/home/ubuntu/.t3/projects/vepol/src/components/Game.tsx:223), [src/components/Game.tsx:448](/home/ubuntu/.t3/projects/vepol/src/components/Game.tsx:448)). Existing control tests cover simultaneous sources and each combat action reaching the engine ([tests/controls.test.ts:12](/home/ubuntu/.t3/projects/vepol/tests/controls.test.ts:12)); mobile API tests cover fullscreen/orientation rejection and late fullscreen cleanup ([tests/mobile.test.ts:111](/home/ubuntu/.t3/projects/vepol/tests/mobile.test.ts:111)).

## Device and deployment limits

The native preview rendered the lobby at 390×844 CSS pixels and the game at 844×390. In portrait, the touch layout showed the accessible “Gira tu teléfono” gate with gameplay controls non-interactive; after landscape resize the gate disappeared. A finished-game result card and both actions fit within the 844×390 viewport. The preview host reports zero touch points and a fine pointer by default; I injected coarse-pointer/touch-point values to inspect the touch layout. A synthetic `PointerEvent` did not change React’s pressed state in that harness, so this is not counted as a successful pointer-input test. No physical iOS or Android device was available.

CI does not validate actual iOS/Android pointer-capture and cancellation semantics, browser fullscreen/orientation behavior on hardware, packet loss over an external network, or multi-process room routing. The README describes one persistent Node process, in-memory rooms, and no cross-instance scaling; restarts close live matches. The measured load test is loopback-only, so it does not establish production bandwidth or capacity.

## Residual risk

The fixed-step scheduler intentionally drops elapsed whole ticks after more than five catch-up steps. This avoids a catch-up spiral, but an event-loop stall longer than about 83 ms slows the match clock relative to wall time until normal stepping resumes. Both players share the same server simulation, so this does not give one peer a private clock advantage.

RISKIEST LINE: [server/ticker.ts:31](/home/ubuntu/.t3/projects/vepol/server/ticker.ts:31) — dropping backlog is the clearest remaining gameplay tradeoff: after a long event-loop stall, match time runs late instead of attempting unbounded catch-up.
